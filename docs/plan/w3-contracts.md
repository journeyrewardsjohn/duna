# Wave 3 contracts (W3-0)

Dated 28 November 2026. Written by the W3-0 schema steward. This is the frozen
interface between the wave-3 backend packages (B1–B11, FAM, L3) and the
wave-4 UI packages (H*, P*). Backend agents implement services behind these
shapes; UI agents build against the demo fixtures. Neither changes a shape
without asking the orchestrator; a schema change goes through
`docs/plan/schema-requests/<WP>.md`.

## What landed

- **One migration, `packages/db/drizzle/0116_w3_domain_backends.sql`**,
  generated by `drizzle-kit generate`, additive only: 65 new tables, new
  nullable or defaulted columns on `courts`, `training_programs`,
  `training_events`, `training_practice_plans`,

  `packages/db/src/w3-domain-backends-migration.test.ts` enforces all of
  this and applies every migration to an empty PGlite database.
- **Rehearsed** on a throwaway branch of production (`duna-production`):
  `packages/db/src/migrate.ts` (the production path) applied 0116 cleanly,
  existing reads and writes spot-checked, branch deleted.

  the demo club and people, covering every value of every state tuple.

  `index.ts`, one prefix in `demo/ids.ts`, as H1 did for health):

## Conventions every package follows

- **Money**: integer minor units + ISO 4217 currency (`w3MoneySchema`,
  `w3AmountSchema`; DB `bigint ... _minor` + `currency` with an upper-case
  CHECK). Percentages are basis points (`w3BasisPointsSchema`). Load is
  0–100 (`w3LoadSchema`).
- **Time**: instants are `timestamp with time zone` / `w3DateTimeSchema`;
  calendar dates `date` / `w3DateSchema`; wall-clock times `time` /
  `w3TimeOfDaySchema` in the row's timezone; weekday 0 = Sunday.
- **States** are `varchar` + CHECK (never a new Postgres enum), exported as
  `const` tuples from the schema file; the contract uses `z.enum(tuple)`.
- **Append-only** tables (trigger): `pay_delivery_events`,
  `premium_subscription_events`, `household_consents`,
  `website_publish_events`. Their foreign keys are `restrict`.
  Money movement is posted to the existing `ledger_journals` /
  `ledger_entries` (append-only, reversal journals); W3 rows point at the
  journal (`ledger_journal_id`).
- **Not implemented yet**: `notImplementedYet()` in
  `routers/not-implemented.ts` throws `NOT_IMPLEMENTED` with a cause marked
  as the expected `provider-not-configured` outcome. The O1 observed
  procedure turns it into `PRECONDITION_FAILED` + "This feature is not
  configured yet.", logs one warning with reason `not-implemented` and never
  reports it. The UI renders the kit's `NotConfigured` state. Delete the
  call when you implement the procedure.
- **Scopes** (existing ones only; the demo actor is player + manager):
  money writes `payments:write` (owner only), team reads/writes
  `members:read` / `members:write`, training `training:read` /
  `training:write`, concierge `messages:read` / `messages:propose` /
  `messages:write`, setup, website and facility `sessions:read` /
  `sessions:write` (stand-in: dedicated scopes are an R3 follow-up).
- **Kill switches** already in the registry: `training.storefront`,
  `training.scene3d`, `team.contractorPayouts`, `concierge.channel.*`,
  `website.workspace`, `facility.owners`. No new flag was needed.
- Each router keeps its `status` placeholder (the seams test uses it).

## Steward decisions where the plan was silent

1. `organizations` was not widened: profile facts live in the 1:1
   `organization_profiles`, Duna Pay state in the 1:1
   `organization_pay_accounts`.
2. The payout policy reuses the existing double-entry ledger for money;
   W3 adds obligations, tranches, delivery events, holds, reserves,
   disputes, refund funding and recoveries around it.
3. `message_channel` and `training_program_status` were **not** extended:
   adding a value widens the TypeScript union that existing non-W3 code
   narrows (`operator-service.ts`, `training-service.ts`), which fails
   typecheck. Concierge tables carry their own checked channel; a cancelled
   program is `cancelled_at` + `archived` (CHECK), derived to `cancelled` in
   the contract. Both are listed for the owning package.
4. `messaging_context_type` was not extended either: a tournament thread uses
   `event`, a club thread `organization`, a person's own Duna thread is a
   `support` conversation with no context.
5. Practice plans live in the `training-programs` seam; drill scenes live in
   `training_drill_scenes` (one per drill version; the validator is code).
6. Team pay tables are prefixed `staff_` to keep them apart from Duna Pay's
   payout tables; W-2 lines can never use the `duna-pay` method (CHECK).
7. Blackouts (no approval) and time off (approval) are separate tables.
8. The legal document key CHECK became a format check (any well-formed key)
   rather than a list, so new documents need no migration.
9. Under-13 children are `household_members` with role `child` and a
   required `account_holder_person_id`; invitations can never be for a
   child (CHECK).

**State machines**

- Account (`organization_pay_accounts.status`, derived on every processor sync, never set by hand): `not-started → in-progress → verifying → ready`; any → `action-needed` (requirements due, not yet past due) → back to `verifying`/`ready`; any → `restricted` (past due or disabled) → `verifying`. `ready` requires charges and payouts enabled (CHECK). Bank: `missing → pending → verified | errored`.
- Obligation: `pending-settlement → awaiting-delivery → partially-released → released`; from any open state → `held` (hold or reserve covers it), `disputed`, `partially-refunded`, `refunded`; `cancelled` when the club cancels before delivery (full refund). Delivery rule by product: court rental, lesson, clinic → `scheduled-end`; event ≤ 7 days → `event-last-day`; program/camp with sessions → `pro-rata-sessions` (optional `start-tranche` ≤ 25% released when the first session ends, only for opted-in organisations in good standing); league or > 7 days without sessions → `pro-rata-weekly`; membership → `membership-period` (later of settlement + 3 business days and `refund_window_ends_at`); credit pack → `credit-pack-reserve` (cash on settlement, 20% of unredeemed paid credits held by the standing reserve; redemption-only for the first 90 days); goods → `goods-fulfilment` (ship-by, then buyer may cancel); digital, in-person, tips → `instant`.
- Tranche: `scheduled → delivered → releasable → released`; `held` while a hold covers it; `reversed` after a refund or lost dispute took it back; `cancelled` if delivery will not happen. `released` iff `released_at` (CHECK). Releasable time = later of settlement, delivery, refund window and first-payout delay.
- Hold: `active → released | applied` (applied = consumed by a refund, dispute loss or set-off).
- Reserve: `proposed → active → under-review → active | released`; active needs start, notice sent and review date (CHECK).
- Dispute: `needs-response → evidence-submitted → under-review → won | lost`; `needs-response → accepted`; `warning-closed` for inquiries. Closed states require `closed_at` (CHECK). Opening places a `dispute` hold and reverses the transfer (journal in `reversal_ledger_journal_id`); a win re-transfers (`outcome_ledger_journal_id`).
- Recovery: `pending → collected | failed | written-off`; order set-off → bank debit → invoice (15 days).

**Decisions where the plan was silent**

- The existing double-entry ledger is the money record; W3 tables reference journals rather than adding a second ledger. "Reversal entries" are reversal journals (`ledger_journals.reversal_of_journal_id`).
- Organisation proceeds are stored and checked: `proceeds = gross − application fee − tax` (CHECK).
- `organization_pay_accounts` is a new 1:1 table instead of more `organizations` columns; the six statuses are a stored cache refreshed by sync.
- Daily stays a value of `payout_interval`; the default remains weekly in the column (no ALTER COLUMN in 0116), B2 writes daily for new organisations.
- Demo actor (player + manager) has `payments:read` but not `payments:write`; writes are owner-only, matching "money changes need the owner".
- Statement descriptors: the board's "bookings" and "lessons" descriptors map to the existing `statement_descriptor` and `payout_statement_descriptor`; a per-product descriptor needs a schema request.

**State machines.**

- Schedule: `draft → active | fallback`; `active | fallback → archived`. At most one `fallback` per staff member (unique index). The schedule in force on a date = the `active` one whose `[effectiveFrom, effectiveTo]` covers it, else the `fallback`.

- Coverage request: `open → asking → covered`; `open | asking → nobody-free | cancelled`; `nobody-free → asking` when someone frees up. `covered` ⇔ `coveredBy` set. One open/asking request per session or training event.
- Offer: `suggested → asked → accepted | declined`; `accepted → assigned`; any non-final → `withdrawn` (another offer was assigned). `assign` may skip `ask` when a manager assigns directly.
- Reasons: `time-off`, `blackout`, `schedule-change`, `no-coach-assigned`, `manual`.

**Who implements.** B3a: service in `services/team-availability/`, suggestions as a pure function in `packages/scheduling/src/coverage.ts` (rank by free, level/kind match, load this week). Approving time off or adding a blackout creates coverage requests for the affected sessions. "Ask" only records the ask; the message is a Concierge Send proposal (B7) that a person confirms. H5 builds the screens.

**Decisions.**

- Blackouts (no approval) and time off (approval) are separate tables, as the plan names them; the UI may show them in one list with a type chip.
- `sessionsNeedingCover` is derived, never stored.
- `sourceText` keeps the sentence a schedule was written from; parsing is B3a's (model proposes, code validates).
- Windows are replaced wholesale on `upsertSchedule` (simpler than per-window edits; the editor sends the full week).
- Weekday 0 = Sunday, times are wall-clock in the schedule's `timezone`.
